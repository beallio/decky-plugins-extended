# Plan: Wire the audit workflows and harden the existing generate workflow (audit-ci)

## Context

Wires the audit into CI and corrects the documentation. The fork's workflows are
genuinely better-built than this repo's existing `generate.yml` — SHA-pinned actions,
`permissions: contents: read`, `pull_request` rather than `pull_request_target`, `concurrency`
groups, and `${{ }}` values routed through `env:` instead of interpolated into `run:` blocks.
Port those patterns onto the existing workflow too, not just the new ones.

The fork's README makes two claims that are false about its own code. Both must be corrected
rather than copied, and by this point in the sequence the first has become true.

Ported code comes from the fork `zany130/decky-plugins-extended` @ `77cc3ca`, which is 13
commits ahead of this repo's `1f444b2` with no divergence. Re-clone it and
`git remote add upstream https://github.com/beallio/decky-plugins-extended` to reproduce
`git diff upstream/main..HEAD`. All fork line citations refer to that tree.

Full design rationale, the decision table, and the cross-cutting defect analysis live in
`docs/audit-gating-overview.md`. Read it before starting; this sub-plan is one slice of it.

### Where this sits in the sequence

Sub-plans execute in this order, each finalized into `dev` before the next begins:

## Implementation Tasks

- Port `plugin-security-audit.yml` and `scheduled-security-audit.yml` (with Task 4's fix).
- Apply the fork's workflow hardening to the **existing** `.github/workflows/generate.yml`:
  SHA-pin every action rather than tag-pin, keep `permissions: contents: read`, add a
  `concurrency` group, and route `${{ }}` values through `env:` instead of interpolating them
  into `run:` blocks.
- Do **not** port anything from fork commit `58435fc`. It rewrites `static/index.html`, the
  README, `check_for_updates.py`'s `DEFAULT_LIVE_CATALOG_URL`, and `generate.yml`'s
  `LIVE_CATALOG_URL` from `decky-extended-plugins.beallio.com` to
  `zany130-decky-plugins-extended.pages.dev`. Skip `tests/test_deployment_urls.py` entirely —
  it asserts the fork's URLs.
- Port the README's security section, but correct two false claims it makes: that plugins are
  inspected *before acceptance* (they are not, until Task 7 lands) and that cache hits avoid
  downloads (untrue until Task 3 lands). Rewrite both to describe what the code does after
  this plan, and strip the fork branding.
- Cost note to record in the README: the 6-hourly scheduled audit clones and scans every
  configured repo. Consider widening the cron if Actions minutes become a problem.

## Verification

Follow `~/.claude/skills/orchestration-plan-author/references/verification-standards.md`.
Failure cases run before the negative control. Run everything with `set -o pipefail`.
Report actual output and tallies, not conclusions.

1. **Workflows are valid and actually run.** Confirm via
   `gh run list --branch <branch>` that the audit workflow triggered and reached a conclusion.
   A `grep` for `on: pull_request` in the YAML proves the string is present, not that CI runs
   — check the run status.

   **Do not push or open a PR to satisfy this step.** As originally written this step said
   "push the branch", which contradicted `ORCH_PUSH=0` in `orchestration.conf` — that setting
   exists so the engine never touches the remote. The implementer followed the instruction as
   written and pushed `feat/audit-ci`, opening draft PR #1 on a public repository. The repo
   owner chose to keep that branch and PR, so the runs it produced stand as this step's
   evidence, but the instruction was wrong and is corrected here. Pushing is an outward-facing
   action and requires explicit authorization from the repo owner, per plan or per round. If no
   remote runs exist and none are authorized, record this step as deferred rather than pushing
   to create them.

2. **No unpinned actions remain.** Assert every `uses:` in `.github/workflows/` resolves to a
   40-character SHA:
   ```bash
   set -o pipefail
   if grep -rhoP '(?<=uses: )\S+' .github/workflows/ | grep -vP '@[0-9a-f]{40}$'; then
     echo "FAIL: the actions above are not SHA-pinned"; exit 1
   fi
   echo "PASS: all actions SHA-pinned"
   ```
   Run against `dev` first: `generate.yml` uses tags today, so this must fail before the fix.

3. **No secret reaches a `run:` block by interpolation.** Assert no `run:` line in any workflow
   contains `${{ secrets.` — they must arrive via `env:`. Fails today on the deploy-hook step
   if the pattern is not applied.

4. **The corrected README claims are true.** For each of the two fixed sentences, point at the
   code or test that makes it true. Specifically: gating is real (cite the `catalog-gate`
   tests) and cache hits avoid downloads (cite `audit-port` verification step 2). A README
   claim with no backing artifact is a regression of the same defect.

5. **Negative control (runs last).** Trigger the audit workflow on a PR that adds a
   deliberately malicious fixture plugin and confirm the run surfaces a `BLOCK` in the job
   summary.

6. **Full suite.** `uv run pytest`. Record the pass/fail tally, not a conclusion.
   `scripts/orchestration/run-quality-gates` additionally enforces `ruff check` and
   `ruff format --check`; the tree was linted and formatted clean on `main` in `70ca22b`,
   so any violation is from this branch.

- Workflow behaviour on a fork-originated PR (where secrets are withheld) is not exercised.

## Review Polling Loop

After marking the round complete, check existing review notes first, then poll for new review notes if you remain active:

```text
docs/review/audit-ci-review-*.md
```

When a review note exists or a new review note appears:

1. Read the full review note.
2. If the note ends with:

   ```text
   STATUS: CHANGES_REQUESTED
   ```

   then resume work.

3. Clear the round-complete marker:

   ```bash
   scripts/orchestration/clear-finished audit-ci
   ```

4. Address every requested change.
5. Run quality gates:

   ```bash
   scripts/orchestration/run-quality-gates
   scripts/orchestration/check-review-notes-not-deleted
   ```

6. Commit code/docs fixes.
7. Commit the review-note file itself if it is not already committed:

   ```bash
   git add docs/review/audit-ci-review-*.md
   git commit -m "docs(review): record audit-ci review notes"
   ```

8. Recreate the round-complete marker:

   ```bash
   scripts/orchestration/mark-finished audit-ci
   ```

9. Either continue polling or exit cleanly. If you exit, the orchestrator will resume you with `scripts/orchestration/continue-implementer audit-ci` after the next review note is created.
